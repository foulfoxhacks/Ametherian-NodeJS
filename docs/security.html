Security approach

Threat models, bounded resources, and evidence-backed claims.

Reviewed November 2026 · Source repository ↗

Security by design#

Security is a design and maintenance requirement, not a marketing guarantee. Each package must document trust boundaries, threat model, assumptions, and known limitations.

Threat modeling#

Threat modeling should consider SSRF, DNS rebinding, redirect policy bypasses, TLS hostname and certificate validation, credential exposure, unsafe parsing, prototype pollution, decompression bombs, unbounded resource use, cache poisoning and isolation, filesystem traversal, concurrency races, and dependency or build-chain compromise.

Secure engineering practices#

  • Reusing mature cryptographic, TLS, compression, and parsing primitives.
  • Bounding resource use and avoiding secret logging.
  • Validating redirects and protocol transitions.
  • Testing malformed and adversarial inputs.
  • Tracking dependency provenance and adding regression tests for confirmed vulnerabilities.
  • Requiring human review for security-sensitive fixes.

Vulnerability intelligence#

Vulnerability intelligence may draw on OSV, GitHub Security Advisories, NVD, CISA Known Exploited Vulnerabilities, Node.js security advisories, and upstream advisories. Any ingestion must preserve source attribution, timestamps, affected-version ranges, confidence, and freshness. Intelligence informs review and testing; it must not trigger unreviewed production changes.

Coordinated disclosure#

Security reports must follow the security policy. Do not post exploit details publicly before coordinated disclosure.
