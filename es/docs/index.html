Cómo leer la documentación#

  • Planificar no es implementar. Una capacidad, un nombre de paquete o un control de seguridad descritos son una dirección hasta que existen código, pruebas, documentación y una publicación.
  • Las afirmaciones necesitan pruebas. Las afirmaciones de compatibilidad, rendimiento, fiabilidad y seguridad deben ser reproducibles o estar marcadas explícitamente como objetivos.
  • Las fechas no son promesas. La hoja de ruta va por etapas. Los compromisos de publicación no se anuncian hasta que el alcance, la responsabilidad y la capacidad están definidos.
  • Los nombres de terceros indican contexto. Axios, Undici, Node.js y OpenJS se mencionan para describir el ecosistema y sus condiciones, no para sugerir afiliación ni respaldo.
