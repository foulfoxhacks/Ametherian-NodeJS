<h1>Contributing</h1>
<p>Ametherian is currently gathering feedback on its direction and proposed architecture.</p>
<h2>Before contributing</h2>
<ul>
<li>Read the project status and security approach.</li>
<li>Keep proposals focused and explain the developer problem they address.</li>
<li>Distinguish existing behavior from proposed behavior.</li>
<li>Include runtime and compatibility considerations.</li>
<li>For security-related proposals, include the threat, trust boundary, mitigation, and a testable acceptance criterion.</li>
</ul>
<h2>Proposed contribution standards</h2>
<p>Future implementation repositories should use:</p>
<ul>
<li>TypeScript strict mode where TypeScript is used</li>
<li>Consistent formatting and linting</li>
<li>Unit, integration, compatibility, and security regression tests</li>
<li>Documented public APIs and deprecation policy</li>
<li>Dependency review and reproducible lockfiles</li>
<li>Small, reviewable pull requests</li>
<li>Changelogs for user-visible changes</li>
</ul>
<h2>Pull request expectations</h2>
<p>A pull request should explain why the change is needed, what changed, how it was tested, what compatibility effects it has, and whether documentation is updated. Do not include secrets, private vulnerability details, generated credentials, or unrelated formatting churn.</p>
