セキュリティ方針

設計段階からのセキュリティ#

セキュリティは設計と保守の要件であり、宣伝用の保証ではありません。各パッケージは、信頼境界、脅威モデル、前提、既知の制限を文書化しなければなりません。

脅威モデリング#

脅威モデリングでは、SSRF、DNS リバインディング、リダイレクトポリシーの回避、TLS のホスト名と証明書の検証、認証情報の漏えい、安全でないパース、プロトタイプ汚染、解凍爆弾、無制限のリソース使用、キャッシュポイズニングと分離、ファイルシステムのトラバーサル、並行処理の競合、依存関係やビルドチェーンの侵害を考慮すべきです。

安全なエンジニアリング手法#

  • 成熟した暗号、TLS、圧縮、パースのプリミティブを再利用する。
  • リソース使用に上限を設け、秘密情報をログに残さない。
  • リダイレクトとプロトコルの切り替えを検証する。
  • 不正な入力や敵対的な入力をテストする。
  • 依存関係の出所を追跡し、確認された脆弱性には回帰テストを追加する。
  • セキュリティに関わる修正には人によるレビューを必須にする。

脆弱性インテリジェンス#

脆弱性インテリジェンスには、OSV、GitHub Security Advisories、NVD、CISA Known Exploited Vulnerabilities、Node.js のセキュリティアドバイザリ、上流プロジェクトのアドバイザリを利用できます。取り込みの際は、情報源、タイムスタンプ、影響を受けるバージョン範囲、確度、鮮度を保持しなければなりません。インテリジェンスはレビューとテストの指針であり、レビューされていない本番環境の変更を引き起こしてはなりません。

協調的な開示#

セキュリティの報告は セキュリティポリシーに従ってください。協調的な開示の前に、エクスプロイトの詳細を公開しないでください。
